# Сайт NUR Invest

Сайт компании NUR Invest: продажа бытовой техники, мебели, электроники и других товаров с оплатой частями.
Цена товара фиксируется в договоре заранее, без процентов по займу и без штрафов за просрочку.

Стек: **Next.js 16 (App Router) + React 19 + TypeScript**, валидация на **zod**, тесты на **Vitest**.
Стили — собственная дизайн-система на CSS-переменных (`src/app/globals.css`), без UI-библиотек.

## Быстрый старт

Нужен Node.js 20.9 или новее (проверено на Node.js 22).

```bash
cd web
npm install
cp .env.example .env.local      # заполните SESSION_SECRET и при желании контакты
npm run dev                     # http://localhost:3000
```

При первом запуске создаётся файл данных `.data/db.json` с категориями и демо-товарами.

Создать первого сотрудника (пароль спросит в терминале, в файл попадёт только хеш):

```bash
npm run admin:create -- --email admin@example.ru --name "Имя Фамилия" --role admin
npm run admin:create -- --email manager@example.ru --name "Менеджер" --role manager
npm run admin:create -- --email old@example.ru --disable   # отключить доступ
```

Вход в админ-панель: `/admin`.

## Модель данных

`src/lib/types.ts`: `Category`, `Product` (с полем `source` для товаров партнёров: название партнёра, артикул,
ссылка), `Lead` (заявка с историей статусов и фактом согласия на ПДн), `Order` (сделка с графиком),
`Payment` (попытка оплаты одного платежа графика: сумма в копейках, ключ идемпотентности, обработанные
уведомления, журнал событий), `AdminUser` (роль, хеш пароля, версия сессий), `SiteSettings`.

## Калькулятор

Формула и таблица наценок перенесены из исходного калькулятора в корне репозитория (`js/script.js`):

- цена продажи = стоимость товара + наценка продавца по таблице (зависит от срока и наличия взноса),
  либо заранее согласованная цена продажи (поле в калькуляторе или в карточке товара);
- первоначальный взнос — от 25% **стоимости товара**, по умолчанию 25%;
- остаток делится на равные платежи, округлённые вверх до 10 ₽; последний платёж — остаток,
  поэтому сумма всех платежей **ровно равна** цене продажи.

Отличие от старого калькулятора: там округление увеличивало итоговую сумму на несколько рублей,
здесь итог всегда совпадает с ценой продажи. Значения меняются в `src/config/terms.ts`.

## Заявки

Заявка проверяется на клиенте и на сервере одной и той же схемой (`src/lib/validation.ts`) и сохраняется
в хранилище со статусом «Новая». Это **не имитация**: заявки видны в `/admin/leads`.

Для production дополнительно понадобится (не реализовано):

- уведомления менеджерам о новой заявке (Telegram-бот, почта или CRM — нужен выбор владельца);
- PostgreSQL вместо JSON-файла (см. ниже).

## WhatsApp

Номер задаётся одной переменной `NEXT_PUBLIC_WHATSAPP_PHONE` (`src/config/site.ts`, `src/lib/whatsapp.ts`).
Кнопки есть в шапке, плавающая кнопка, в карточках и на странице товара, в калькуляторе, в форме заявки.
Пока номер не задан, кнопки ведут на форму заявки, а плавающая кнопка скрыта. Номер встраивается в сборку,
поэтому после изменения нужно пересобрать сайт.

## Админ-панель и безопасность

- Пароли — только хеш scrypt (`scripts/password-hash.mjs`), минимум 12 символов.
- Сессия — подписанная HMAC-SHA256 httpOnly-cookie на 8 часов (`SESSION_SECRET`), `Secure` в production,
  `SameSite=Lax`. Смена пароля или отключение пользователя сразу завершают его сессии.
- Защита маршрутов в три слоя: `src/proxy.ts` (нет подписи — на вход), проверка на каждой странице
  (`requireAdminPage`), проверка прав в каждом серверном действии (`requireAdminAction`).
- Роли: **менеджер** — заявки, просмотр сделок и платежей; **администратор** — ещё каталог, настройки,
  создание сделок и ссылок на оплату (`src/lib/auth/permissions.ts`).
- Ограничение попыток входа и отправки заявок, одинаковое время ответа для существующих и несуществующих email.
- Заголовки безопасности (CSP, X-Frame-Options, nosniff и др.) — `next.config.ts`; админка и `/pay` не индексируются.

## Онлайн-оплата: T-Bank Интернет-эквайринг

**Почему T-Bank.** Официальная документация (https://developer.tbank.ru/eacq/api), платёжная форма банка
(клиент вводит карту на стороне банка, сайт карты не видит — требования PCI DSS к сайту минимальны),
каждое уведомление подписано токеном SHA-256, который можно проверить, есть тестовые терминалы и онлайн-касса
для чеков 54-ФЗ. Похожий по архитектуре вариант — ЮKassa, но её уведомления не подписываются
(проверка только по IP и повторным запросом), поэтому выбран T-Bank.

**Сценарий:**

1. Администратор создаёт сделку с графиком и нажимает «Создать ссылку» у нужного платежа.
2. Сервер атомарно резервирует попытку оплаты (ключ идемпотентности `сделка:платёж:попытка`) и вызывает `Init`.
   Повторное нажатие возвращает ту же ссылку, оплаченный платёж нельзя оплатить снова.
3. Клиент получает ссылку `/pay/<id>` (например, в WhatsApp) и переходит на платёжную форму банка.
4. Банк присылает уведомление на `/api/payments/tbank/notification`. Сервер проверяет подпись и терминал,
   сопоставляет платёж по `OrderId` и `PaymentId`, сверяет сумму, а для успешных статусов дополнительно
   запрашивает `GetState`. Повторные и запоздавшие уведомления не меняют результат.
5. Статус «Оплачен» появляется только после этого. Возврат клиента на сайт статус не меняет.

**Режимы:** `PAYMENTS_PROVIDER=disabled` (по умолчанию) — ничего не создаётся, интерфейс прямо говорит,
что оплата не подключена. `tbank` + `PAYMENTS_MODE=test` — только тестовый терминал `…DEMO`.
`PAYMENTS_MODE=live` включается лишь с `PAYMENTS_LIVE_CONFIRMED=I_CONFIRM_LEGAL_REVIEW`.

**Что сделать владельцу для подключения:**

1. Заключить договор интернет-эквайринга с T-Bank, пройти проверку сайта банком (банк проверяет оферту,
   реквизиты, контакты, описание товаров и условий возврата на сайте).
2. В личном кабинете создать магазин и получить **тестовый** терминал. Заполнить `TBANK_TERMINAL_KEY`,
   `TBANK_PASSWORD`, `PAYMENTS_PROVIDER=tbank`, `PAYMENTS_MODE=test`, `NEXT_PUBLIC_SITE_URL` (https).
3. Указать в настройках терминала адрес уведомлений `https://<домен>/api/payments/tbank/notification`
   (сайт также передаёт его в каждом запросе).
4. Пройти тестовые сценарии банка на тестовом терминале.
5. Подключить онлайн-кассу и вместе с бухгалтером выбрать систему налогообложения, ставку НДС и признаки
   расчёта для взноса и платежей по графику (`TBANK_RECEIPT_*`).
6. Только после юридической и шариатской проверки — боевой терминал, `PAYMENTS_MODE=live`
   и `PAYMENTS_LIVE_CONFIRMED=I_CONFIRM_LEGAL_REVIEW`.

## Запуск в production

Сейчас данные хранятся в JSON-файле — это подходит для разработки и небольшого пилота **на одном сервере
с постоянным диском** (VPS, Docker с томом). Не подходит для бессерверных платформ и нескольких экземпляров.

Перед полноценным запуском:

- перенести хранилище в **PostgreSQL**, размещённый **в России** (требование 152-ФЗ о локализации ПДн):
  заменить реализацию `readDb`/`mutateDb` в `src/lib/db/store.ts` или функции в `src/lib/data/*`;
  модель из `src/lib/types.ts` переносится таблица в таблицу; рекомендуется транзакция с уникальным
  индексом на `payments.idempotency_key`;
- ограничение частоты запросов перенести в Redis или на обратный прокси;
- настроить HTTPS, резервное копирование данных, мониторинг `/api/health` и логов;
- задать `SESSION_SECRET`, `TRUST_PROXY=true` (если есть свой прокси), `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`
  при нескольких экземплярах;
- заменить демо-товары реальными (`SEED_DEMO_PRODUCTS=false` для новой базы);
- добавить уведомления о заявках и Open Graph-изображение (`src/app/opengraph-image.png`).

```bash
npm ci && npm run build && npm run start   # порт 3000, за nginx с HTTPS
```

## Что нужно проверить до публикации

Юристом:

- модель «купля-продажа товара с оплатой частями» и договор (ст. 488–489 ГК РФ), порядок перехода права
  собственности, возврат и обмен по закону «О защите прав потребителей»;
- допустимость формулировок «без процентов» и «без штрафов за просрочку» с учётом условий договора;
- что деятельность не требует лицензии и не подпадает под регулирование потребительского кредитования;
- публичная оферта, политика ПДн, согласие, хранение ПДн в РФ, уведомление Роскомнадзора;
- чеки 54-ФЗ для взноса и платежей по графику.

Компетентным шариатским экспертом:

- что сделка оформляется как продажа товара, который принадлежит компании на момент продажи;
- что наценка фиксируется до сделки и не меняется при просрочке или досрочной оплате;
- порядок действий при просрочке без штрафов и пеней, порядок возврата товара;
- допустимость использования эквайринга и формулировок на сайте.

До получения документального подтверждения сайт **не** заявляет о шариатском одобрении, фетвах или сертификации —
только аккуратную формулировку из `src/config/terms.ts`.
