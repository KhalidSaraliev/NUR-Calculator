# NUR Chat — архитектура (Этап 1)

## Общая схема

```
nur-chat/
├── backend/            # NestJS API (готов, этап 1)
│   ├── prisma/
│   │   └── schema.prisma
│   └── src/
│       ├── auth/       # SMS OTP + JWT
│       ├── users/      # профиль, админ. управление пользователями
│       ├── prisma/     # PrismaService (singleton-подключение к БД)
│       └── common/     # guards, decorators
├── frontend/
│   ├── mobile/         # React Native + Expo (iOS/Android) — этап 2+
│   └── web/            # React + TypeScript — этап 2+
├── admin-panel/        # Web Admin Panel — этап 6
├── database/           # миграции/сиды (генерируются Prisma)
└── documentation/
```

## Почему такой стек

- **NestJS** — модульная архитектура "из коробки" (DI, guards, pipes),
  та же ментальная модель, что у Angular — удобно масштабировать
  на 1000+ сотрудников и десятки разработчиков в команде.
- **Prisma + PostgreSQL** — типобезопасный доступ к БД, миграции,
  подходит для реляционных данных чата (пользователи, чаты, сообщения).
- **Socket.io** (подключается на этапе "Личные чаты") — real-time доставка
  сообщений, статусов "печатает...", online/offline.
- **S3-совместимое хранилище (MinIO локально / AWS S3 или любой
  S3-совместимый провайдер в проде)** — фото/видео/документы не хранятся
  в БД, только метаданные (модель `FileAsset`).
- **JWT (access 15 мин + refresh 30 дней, хранится хэш в БД)** —
  стандартная схема для мобильных + web клиентов.

## Модульная граница backend (NestJS)

| Модуль | Отвечает за |
|---|---|
| `AuthModule` | OTP по SMS, выдача/обновление JWT |
| `UsersModule` | профиль, статусы, админ. действия над сотрудниками |
| `PrismaModule` | единая точка доступа к БД (глобальный модуль) |
| `ChatsModule` | личные чаты, сообщения, WebSocket-шлюз (готово, Этап 2) |
| `GroupsModule` | групповые чаты, роли участников, закреплённые сообщения (готово, Этап 3) |
| `FilesModule` | загрузка в S3, "Файлы компании"/"Файлы группы" (готово, Этап 4) |
| `NotificationsModule` | push, уведомления о сообщениях, упоминания `@` (готово, Этап 5) |
| `AdminModule` | dashboard, отделы, компания, обзор групп (готово, Этап 6) |

## Что уже реализовано (Этап 1)

1. Полная схема БД (все сущности проекта — компании, отделы,
   пользователи, чаты, сообщения, файлы), чтобы миграции не пришлось
   ломать на следующих этапах.
2. Регистрация: `POST /api/v1/auth/otp/request` →
   `POST /api/v1/auth/otp/verify` → если новый пользователь,
   `POST /api/v1/users/complete-profile/:phone`.
3. JWT-авторизация (`JwtAuthGuard`) и ролевая модель
   (`RolesGuard` + `@Roles(...)`).
4. Профиль пользователя: `GET /api/v1/users/me`,
   `PATCH /api/v1/users/me`.
5. Первые админ-эндпоинты: список сотрудников компании,
   блокировка пользователя.

## Что уже реализовано (Этап 2 — `ChatsModule`)

1. Личные чаты (тип `DIRECT`): `POST /api/v1/chats/direct` находит
   существующий чат между двумя сотрудниками или создаёт новый.
2. Сообщения (REST, `ChatsController`):
   - `GET /chats/:chatId/messages` — история с пагинацией по курсору
   - `POST /chats/:chatId/messages` — отправка (текст и/или вложения)
   - `PATCH /chats/:chatId/messages/:messageId` — редактирование (только автор)
   - `DELETE /chats/:chatId/messages/:messageId` — soft-delete (автор
     или админ чата)
   - `PATCH /chats/:chatId/messages/:messageId/pin` — закрепить/открепить
   - `POST /chats/:chatId/messages/:messageId/forward` — переслать в другой чат
   - `PATCH /chats/:chatId/read` — отметить чат прочитанным
   - `GET /chats/search?query=...&chatId=...` — поиск по тексту сообщений
3. Real-time (`ChatsGateway`, Socket.io, namespace `/chats`):
   события `message:send/new`, `message:edit/updated`,
   `message:delete/deleted`, `typing:start/stop` → `typing:update`,
   `chat:read`, `presence:update` (online/offline). Подключение
   авторизуется JWT-токеном в `handshake.auth.token`.
4. Модель прочтения (`MessageRead`) уже используется для галочек
   "прочитано" — `markChatAsRead` создаёт записи для всех непрочитанных
   сообщений собеседника.

REST остаётся источником истины (история, поиск, пагинация); WebSocket —
для мгновенной доставки и presence. Формат сообщений одинаковый в обоих
API, так что клиент может использовать оба взаимозаменяемо.

### Известное ограничение Этапа 2 — закрыто на Этапе 3

Раньше сокет присоединялся к комнатам чатов только при подключении.
Теперь `ChatsController`/`GroupsController` сразу после создания
личного чата или группы (и после добавления участников) вызывают
`ChatsGateway.joinUserToRoom(userId, chatId)`, которая через
`server.in('user:<id>').socketsJoin('chat:<id>')` подключает уже
активный сокет пользователя к новой комнате без переподключения.

## Что уже реализовано (Этап 3 — `GroupsModule`)

Группа — это тот же `Chat` (тип `GROUP`), поэтому отправка/редактирование/
удаление/пересылка/закрепление/поиск сообщений уже работают для групп
"бесплатно" — используются те же эндпоинты `ChatsController`
(`/chats/:chatId/messages`, ...), просто `chatId` = id группы.

Новое в `GroupsController`:

| Метод | Путь | Права |
|---|---|---|
| POST | `/groups` | любой сотрудник компании — создатель становится `OWNER` |
| GET | `/groups/:id` | участник группы |
| PATCH | `/groups/:id` | название/описание/фото — `ADMIN`/`OWNER` |
| POST | `/groups/:id/members` | добавить участников — `ADMIN`/`OWNER` |
| DELETE | `/groups/:id/members/:userId` | удалить участника — `ADMIN`/`OWNER`, либо сам участник (выход) |
| PATCH | `/groups/:id/members/:userId/role` | назначить/снять администратора — только `OWNER` |
| POST | `/groups/:id/leave` | выйти из группы |
| GET | `/groups/:id/pinned` | список закреплённых сообщений группы |

Владельца группы нельзя удалить или понизить в роли — только он сам может
покинуть группу (тогда группа временно остаётся без владельца; передача
владения — кандидат на доработку перед продакшеном).

Раздел "Файлы группы" из ТЗ появится на Этапе 4 вместе с `FilesModule`
(нужна реальная загрузка в S3, сейчас `FileAsset` — это только схема).

## Что уже реализовано (Этап 4 — `FilesModule`)

Двухшаговый флоу, как в WhatsApp/Telegram: сначала загружаем файл(ы),
получаем их `id`, потом отправляем сообщение со ссылкой на эти `id`.

1. `POST /files/upload` (`multipart/form-data`, поле `files`, до 10 файлов
   за раз — "отправка нескольких фото") → возвращает массив `FileAsset`
   с временной подписанной ссылкой (`url`, живёт 1 час, продлевается при
   каждом запросе к файлу).
2. Фото автоматически сжимаются перед загрузкой: ресайз до 1920px по
   большей стороне + JPEG качество 80 (`sharp`).
3. Категория (`IMAGE`/`VIDEO`/`VOICE`/`DOCUMENT`/`ARCHIVE`/`OTHER`)
   определяется по MIME-типу автоматически.
4. `POST /chats/:chatId/messages { attachmentIds: [...] }` — прикрепляет
   уже загруженные файлы к сообщению (эндпоинт уже существовал с Этапа 2).
5. `GET /files/company?category=` — раздел "Файлы компании": все файлы,
   кто загрузил, дата загрузки, с фильтром по типу.
6. `GET /files/group/:groupId` — "Файлы группы": всё, что отправлялось
   вложением в конкретный чат (доступно только участникам).
7. `DELETE /files/:id` — удалить файл (сам загрузивший или
   OWNER/ADMIN компании) — удаляется и из S3, и из БД.

Хранилище — S3-совместимое (MinIO локально, `docker-compose.yml` уже
поднимает его на портах 9000/9001; в проде — любой S3-совместимый
провайдер, меняется только `.env`).

### Что осталось за рамками backend

- Скорость воспроизведения голосовых (1x/1.5x/2x), предпросмотр фото/видео
  до отправки — это UI-логика мобильного/web-клиента, backend только
  хранит и отдаёт файл.
- Проверка файлов антивирусом/на вредоносный контент — стоит добавить
  перед продакшеном (например, ClamAV перед `storage.upload`).

## Что уже реализовано (Этап 5 — `NotificationsModule`)

Добавлены модели `Notification` и `PushToken` (устройство ↔ пользователь,
для FCM/APNs/Web Push).

1. `POST /notifications/push-token { token, platform }` — регистрация
   устройства (`IOS`/`ANDROID`/`WEB`), вызывается мобильным/web-клиентом
   при получении FCM-токена.
2. `DELETE /notifications/push-token/:token` — отвязать устройство (logout).
3. `GET /notifications?unreadOnly=true` — лента уведомлений пользователя.
4. `PATCH /notifications/:id/read` и `PATCH /notifications/read-all` —
   отметить прочитанным.
5. **Уведомления о новых сообщениях** — `ChatsService.sendMessage` после
   создания сообщения (не блокируя ответ API) вызывает
   `NotificationsService.notifyNewMessage`: всем участникам чата, кроме
   автора и кроме тех, у кого чат заглушён (`ChatMember.isMuted`).
6. **Упоминания через `@`** — текст сообщения парсится на `@Имя` /
   `@ИмяФамилия`, сопоставляется с участниками чата; совпавшим
   отправляется отдельный тип уведомления `MENTION` вместо обычного.
7. **Уведомления групп** — `GroupsService` уведомляет при добавлении в
   группу (`ADDED_TO_GROUP`) и при изменении роли (`ROLE_CHANGED`).
8. Каждое уведомление одновременно: (а) сохраняется в БД для истории/
   бейджа непрочитанных, (б) уходит через `PushService` на все
   зарегистрированные устройства пользователя.

`PushService` — dev-заглушка (пишет в лог); для реальной отправки на
iOS/Android/Web нужно подключить `firebase-admin` (Firebase Cloud
Messaging закрывает все три платформы одним SDK — рекомендуемый выбор).

### Осознанное упрощение

Список уведомлений сейчас обновляется только через REST (`GET
/notifications`), без отдельного WebSocket-события — чтобы не заводить
циклическую зависимость `NotificationsModule ↔ ChatsModule` на этом
этапе. Бейдж непрочитанных на клиенте можно обновлять по факту
получения push либо коротким поллингом; при необходимости live-событие
`notification:new` можно добавить через `@nestjs/event-emitter` вместо
прямой инъекции гейтвея.

## Что уже реализовано (Этап 6 — `AdminModule` + Admin Web Panel)

### Backend: `AdminModule`

Все эндпоинты защищены `RolesGuard` (`OWNER`/`ADMIN`):

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/admin/dashboard` | сотрудники / активные сейчас / сообщения / файлы |
| GET, PATCH | `/admin/company` | название и логотип компании |
| GET, POST | `/admin/departments` | список / создание отдела |
| PATCH, DELETE | `/admin/departments/:id` | переименовать / удалить отдел |
| GET | `/admin/groups` | все группы/каналы компании (не только "мои") |

Плюс в `UsersController` (уже существовал с Этапа 1, дополнен):
`PATCH /users/:id/role` (только `OWNER`) и `DELETE /users/:id` (только
`OWNER`, удаление сотрудника из компании).

### Frontend: `admin-panel/` (React + TypeScript + Vite + Tailwind)

Отдельное web-приложение поверх уже готового API — вход тем же
SMS-кодом, что и в мессенджере, но с проверкой роли (`OWNER`/`ADMIN`)
на клиенте и на каждом запросе к `/admin/*` — на сервере.

Экраны: **Дашборд** (4 карточки статистики), **Сотрудники** (роль,
отдел, статус, блокировка/удаление), **Отделы** (создание/переименование/
удаление), **Группы** (обзор всех групп и каналов компании, только
просмотр — управление участниками остаётся в приложении), **Настройки**
(название и логотип компании).

Визуальный стиль — по ТЗ: тёмно-зелёный/изумрудный (`#0B3D2E`) sidebar,
приглушённое золото (`#C9A227`) как единый акцент (подчёркивание
активного пункта меню, "нить" вдоль края sidebar, подчёркивание под
цифрами в карточках), белый фон контента. Шрифты: **Fraunces** для
вордмарка/заголовков, **Inter** для интерфейса, **IBM Plex Mono** для
цифр в dashboard — сочетание, которое встречается редко у типовых
SaaS-админок, и должно выделять NUR Chat среди шаблонных решений.

### Запуск admin-panel

```bash
cd admin-panel
cp .env.example .env   # VITE_API_URL, по умолчанию http://localhost:3000/api/v1
npm install
npm run dev
```
Откроется на `http://localhost:5173`. Для входа нужен пользователь с
ролью `OWNER` или `ADMIN` (первый зарегистрированный в компании
сотрудник — см. `UsersService.completeProfile` — автоматически
становится `OWNER`).

### Осознанные упрощения

- Создание/участники групп управляются только в приложении (Этапы 2–3);
  в admin-panel — просмотр, соответствует ТЗ ("Управление: ... группы"
  как часть обзора, детальное редактирование — через основной UI чата).
- "Права доступа" реализованы как смена роли (`EMPLOYEE` /
  `DEPARTMENT_HEAD` / `ADMIN`) — более гранулярная ACL-система (доступ
  к конкретным разделам) осталась бы over-engineering для этого этапа.
